# Программа и методика испытаний SCII-гейта на стенде ArduPilot

Редакция 1.0 от 30.10.2026. Документ фиксируется до прогона сценариев. Его SHA-256 и SHA-256 плана (testbed/plan.json) записываются в docs/PMI.sha256 до запуска `scenarios.py run`. После прогона ПМИ и план не меняются. Расхождения с планом разбираются в протоколе испытаний.

## 1. Объект испытаний

Объект испытаний — программная реализация метода оценки целостности цепочки сборки и обновления по графу доказательств (scii-gate 0.1.0, каталог `scii/`). Реализация вычисляет формулы (1)–(4) статьи ВАК-2 и проверяет свидетельства по комплекту поставщика и политике получателя.

Цепочка, на которой проводятся испытания: прошивка ArduPilot Copter-4.5.7 для полётного контроллера CubeOrange (board_id 140). Исходный код: https://github.com/ArduPilot/ardupilot, тег Copter-4.5.7, коммит 2a3dc4b7bf2507120f7378a7b2fde73185e0c325. Механизм защищённой загрузки: подписанный дескриптор приложения ArduPilot (app_descriptor_signed, EdDSA Monocypher), ключи загрузчика задаёт поставщик.

## 2. Цели испытаний

1. Проверить, что проверки гейта ставят состояния P, N и F по реальным файлам комплекта так, как задумано для каждого сценария.
2. Проверить, что правило допуска даёт ожидаемые решения для штатных сценариев и сценариев нарушителя.
3. Измерить время работы гейта на одном комплекте.
4. Зафиксировать измеримые свойства апстрима: какие свидетельства публикует проект ArduPilot для выпуска и воспроизводится ли официальный образ сборкой из тега.

## 3. Стенд

| Компонент | Значение |
|---|---|
| Хост | облачная Linux-машина, 2 ядра Intel Xeon 2,1 ГГц, ядро Linux 6.18 |
| Python | 3.11.15 (виртуальное окружение uv), pymonocypher 3.1.3.2, pymavlink |
| Тулчейн | gcc-arm-none-eabi-10-2020-q4-major, SHA-256 21134caa478bbf5352e239fbc6e2da3038f8d2207e089efc96c3b55f1edcd618, тот же, что задаёт install-prereqs тега |
| Подпись и аттестации | cosign v2.4.1 (ключи ECDSA P-256, без публичного журнала прозрачности: `--tlog-upload=false`), GnuPG 2.4.4 для тегов |
| Статический анализ | flawfinder 2.0.20 |
| Испытание в симуляторе | ArduCopter SITL того же коммита, сценарий testbed/sitl_smoke.py |

Роли и ключи (testbed/keys.sh): сборочный агент (builder), контрольный пересборщик (independent_builder), поставщик до и после смены ключа (vendor, vendor2), хранилище артефактов (repository), статический анализ (sast), испытания (tester), нарушитель (attacker). Открытые ключи лежат в testbed/policy/keys, их SHA-256 в testbed/policy/keys.SHA256SUMS. Закрытые ключи в репозиторий не входят.

## 4. Профиль политики

Профиль profiles/ardupilot_cubeorange.json повторяет пример статьи. Граф из пяти стадий: v1 источник, v2 сборка (обязательная), v3 репозиторий артефактов, v4 пакет обновления (обязательная), v5 устройство. Рёбра: (v1, v2) сильная, (v2, v3) критическая, (v3, v4) сильная, (v4, v5) сильная. Шкала классов: слабая 0,2, средняя 0,5, сильная 0,8, критическая 1,0. Веса α и обязательные свидетельства (s22, s42) те же, что в статье.

Каждому типу свидетельства сопоставлена проверка. Ключи и ожидаемые значения берутся только из политики получателя (testbed/policy/policy.json).

| Тип | Что предъявляет поставщик | Как проверяет гейт | P / N / F |
|---|---|---|---|
| s11 подписи коммитов | объект коммита | SHA-1 объекта равен закреплённому коммиту, подпись gpgsig | N без подписи; F, если коммит другой |
| s12 рецензирование | аттестация роли reviewer | подпись роли, результат APPROVED | на стенде не предъявляется |
| s13 статический анализ | аттестация sast, привязанная к коммиту | подпись роли sast, статус COMPLETED | F при чужом ключе или другом коммите |
| s14 подписанный тег | объект тега OpenPGP | подпись ключом из политики, отпечаток, объект тега равен коммиту, имя тега | N без подписи; F при чужом ключе или коммите |
| s21 подпись сборочного агента | ссылка шага in-toto link v0.3 | подпись роли builder над образом, коммит в materials | F при другом образе, ключе или источнике |
| s22 provenance (обяз.) | SLSA provenance v1 | подпись builder, builder.id, коммит источника, SHA-256 тулчейна | то же |
| s23 воспроизводимая сборка | аттестация пересборки от builder | подпись, коммит, вердикт MATCH и равенство дайджестов | F при MISMATCH; N при незакреплённом тулчейне |
| s24 контрольная пересборка | аттестация пересборки от independent_builder | то же, ключ контрольного пересборщика | то же |
| s31 неизменность | журнал хранилища, подписанный ключом хранилища | дайджест записи равен образу из пакета | F при расхождении |
| s32 право записи | тот же журнал | загрузивший входит в repository_writers | F при чужом загрузившем |
| s41 SBOM | CycloneDX 1.5 в аттестации builder | все закреплённые зависимости (13 позиций) совпадают | F при подмене |
| s42 подпись пакета (обяз.) | подпись cosign файла .apj | ключ поставщика из политики | F при изменении пакета или чужом ключе |
| s43 испытания | аттестация test-result v0.1 от tester | подпись, результат PASSED | F при FAILED или чужом ключе |
| s51 защищённая загрузка | подпись в дескрипторе образа | тот же алгоритм, что check_good_firmware_signed: CRC частей образа и EdDSA над образом без дескриптора, ключи загрузчика из политики | N без дескриптора; F при неверных CRC или подписи |
| s52 защита от отката | версия в подписанной части образа | версия из AP_FWVersion выше установленной на устройстве (4.5.6) | N без подписанного дескриптора; F при откате |
| s53 привязка к устройству | board_id образа | равен плате устройства (140) | F при другой плате |
| s54 аппаратная аттестация | не предъявляется | проверки нет, устройства на стенде нет | N |

Связь стадий. Гейт не принимает от поставщика отдельный файл сборки. Он восстанавливает образ сборки из пакета: обнуляет в подписанном дескрипторе ровно те 76 байт, которые записывает Tools/scripts/signing/make_secure_fw.py. Свидетельства стадий v2 и v3 проверяются против дайджеста этого образа. Пакет, не полученный из аттестованной сборки, не может опереться на её свидетельства.

## 5. Порог

Порог задаётся процедурой статьи: θ равен R_P^min эталонной записи. Эталонная запись Э — набор свидетельств, который стенд может обеспечить для цепочки на основе апстрима ArduPilot. В Э подтверждены все типы, кроме трёх.

1. s11 отсутствует. Коммит 2a3dc4b7 тега не подписан, тег Copter-4.5.7 лёгкий (проверено до испытаний).
2. s12 отсутствует. Рецензирования выпуска на стенде не было, а данных о рецензиях апстрима гейт получить не может.
3. s54 отсутствует. Устройства с аппаратным корнем доверия на стенде нет.

Для Э модель даёт R_P = 0,577, R_P^min = 0,4968, R_P^max = 0,698, R_P^+ = 1,000. Принято θ = 0,496 (R_P^min, округлённое вниз до 0,001).

Чувствительность. При θ = 0,75 (порядок значения из примера статьи) R_P^max(Э) = 0,698 < θ, и ни один сценарий не получает допуска. Причина в стадии источника: при отсутствии s11 и s12 полнота c(v1) = 0,3. Этот результат фиксируется как свойство апстрима, а не как ошибка гейта.

## 7. Измеряемые величины

Для каждого прогона: состояние и причина по каждому из 17 типов свидетельств, R_P, R_P^min, R_P^max, R_P^+, значения при ошибке в классах всех рёбер, G_P, B_P, решение, код возврата, время работы гейта (с), SHA-256 пакета, перечень файлов комплекта.

Для стенда: SHA-256 образов всех сборок, время сборок, совпадение образов при повторной и независимой сборке, совпадение обычной сборки из тега с официальным образом, версии инструментов, SHA-256 исходных файлов гейта, профиля, политик и плана.

## 8. Критерии оценки

1. Для каждого сценария решение гейта совпадает с ожидаемым решением плана.
2. Состояния всех 17 типов свидетельств совпадают с планом.
3. Каждое расхождение по пп. 1 и 2 записывается в протокол с причиной. План и ПМИ после прогона не правятся.

## 9. Порядок проведения

1. `testbed/builds.sh all` и `OLD_TAG=Copter-4.5.5 testbed/builds.sh old`: сборки, хэши, время.
2. `testbed/keys.sh`: ключи ролей.
3. `python testbed/pipeline.py sast`, `python testbed/pipeline.py tests`, `python testbed/pipeline.py chains`: свидетельства и цепочки.
4. `python testbed/scenarios.py plan`, затем запись SHA-256 ПМИ и плана в docs/PMI.sha256.
5. `python testbed/scenarios.py run`: комплекты, прогон гейта, results/results.json, results/summary.md, отчёты по сценариям results/reports/.
6. Протокол испытаний docs/PROTOCOL.md по результатам.

## 10. Ограничения

1. Все роли работают на одном хосте. Независимость контрольной пересборки обеспечена отдельным свежим клоном, отдельным каталогом и отдельным ключом, но не отдельной машиной.
2. Реального CubeOrange нет. Проверка s51 повторяет алгоритм загрузчика программно. Загрузчик с ключами поставщика не собирается и не прошивается.
3. Журнал прозрачности не используется. Поэтому нет защиты по времени подписи и нет отзыва ключей. Журнал хранилища не проверяется на свежесть, и воспроизведение старого журнала в A4 гейт не отличает.
4. SITL-испытание относится к коммиту и SITL-сборке, а не к образу для CubeOrange.
5. Изменения нарушителя моделируются инертными метками и одной подменой подмодуля. Обход проверок самим гейтом не исследуется.
6. Свидетельство s12 на стенде не формируется. Сценариев с его наличием нет.
